### Browser-specific conclusions

- The current strict explicit-ID behavior is a deliberate correctness decision and should remain; only the identity source should change if approved.

### User-prioritized shell/bootstrap conclusion

- The runtime advertises the exact `browser-automation/SKILL.md` path through a native system-prompt catalog or provider-specific skill projection. The agent reads that file, resolves its relative `scripts/browser` reference from the file's containing directory, and invokes the resulting launcher path with Bash. No framework-populated `SKILL_DIR` variable or agent-facing load operation is assumed.
- The skill uses the available Bash/shell execution tool and normally issues one CLI command per tool call.
- The agent maps the former MCP call directly to those command arguments. Normal scripted interaction is `run-script --tab-id ... --script '<JavaScript>' --arg-json '<JSON>'`; coding-agent-owned Bash quoting is not replaced by a complexity-driven temporary file/stdin workflow.
- `--script-file`, `--script-stdin`, and `--arg-file` remain optional when the input already resides there or an actual shell/process constraint prevents faithful direct argv transport.
- The bundled launcher, not the skill prose, human, or agent, resolves its packaged runtime and runs locked `uv` execution.
- First invocation is allowed to take longer while `uv` creates/synchronizes the runtime environment; setup diagnostics stay on stderr and the final command result remains structured stdout.
- `uv` is the host prerequisite. The wrapper should detect its absence and fail clearly rather than installing host software implicitly.
- A bare `browser` command is not discovered automatically and is not the primary skill contract. The skill invokes the resolved bundled `scripts/browser` path and requires no PATH registration or checkout discovery; `browser` is only the generic help/console identity behind that launcher.
