## Goal / Problem Statement

Turn the repository's current stateful `browser-mcp` capability into task-oriented command-line tools and one agent skill, using the incomplete `autobyteus-image-audio` CLI work as a reference without copying its stateless assumptions or documentation gaps.

The intended outcome is an agent-usable browser surface that does not require the agent to start/speak MCP, manually create a Python environment, or reconstruct browser lifecycle rules. The CLI must own deterministic execution and machine contracts; the skill must own concise procedural guidance, observation/action sequencing, safety, recovery, and cleanup conventions.

## Investigation Findings

1. The browser CLI is feasible, but browser state is the central design constraint. A one-process-per-command copy of the current code would lose all `TabManager` state.
2. A real isolated Chrome/Playwright probe proved that the Chrome CDP target ID for a live page remains stable after one Playwright connection closes and a new Playwright runtime reconnects. This supports a daemon-free CLI using browser-owned IDs.
3. The current `UIIntegrator.initialize()` always creates a new page, so existing tool code cannot simply be imported by a CLI. A connection/resolution boundary must attach to the current Chrome context without creating stray pages.
4. Current execution policy is fragmented across `TabManager` and MCP tool modules. The task exposes a boundary/ownership issue and requires refactoring before adding the CLI.
5. The image/audio reference provides useful wrapper, task-command, shared-service, JSON-output, packaging, and validation patterns. It is not a completed skill example, and its canonical design documentation has drifted from current CLI behavior.
6. `run_script` is the only general interaction primitive. First-class click/type/fill commands are not current MCP behavior and are not silently added by this conversion scope.
7. The user explicitly prioritized the shell command experience and confirmed that first invocation must prepare the `uv` project environment behind the CLI/wrapper. The skill should issue ordinary Bash/shell commands and must not expose environment setup as agent work.
8. The user clarified that skill runtimes expose a concrete `SKILL.md` path through a system-prompt catalog or provider-specific projection while the agent reads the file on demand; they do not populate a `SKILL_DIR` shell variable. Therefore `SKILL.md` must contain only bundle-relative resource paths, and the agent must resolve those paths from the advertised entry-point locator before executing Bash.
9. The user subsequently confirmed that AutoByteus is product provenance rather than useful agent vocabulary. The pre-SR-006 candidate leaked it across every agent-facing layer; SR-006 has now replaced that surface with capability-oriented naming and the exact `browser-automation` skill folder.
10. The user then clarified that the CLI should preserve the former MCP call's argument shape rather than teach agents to materialize complex values into files. The generic candidate already has the required direct parser capability; the conflict is the approved skill/design preference and its validation expectations.
11. The user approved making browser automation independent of `brui_core` because the library is very small and the browser capability should evolve within one self-scoped bundle. Direct inspection shows this project uses only two `brui_core` symbols and already wraps them behind `BrowserRuntime`; absorbing only the needed mechanisms is proportionate and avoids copying unrelated/unsafe capabilities.
12. `ARCH-REV-007` found one reachable cross-process lifecycle gap in SR-008: `/json/version` can become ready before the launch owner completes Playwright connection/first-context promotion, allowing a second supported caller to attach while the first still has authority to abort and kill that Chrome group. The per-port gate must therefore cover the complete unavailable→launch→readiness→connect/context→promote/abort transition, and every caller must acquire that gate before treating readiness as durable.

Detailed evidence, the command disposition, and the conversion heuristic are in `cli-conversion-analysis.md`.

## Recommendations

1. Approve browser-owned CDP target IDs as canonical tab identity so each CLI invocation can connect, act, disconnect, and exit without a daemon.
2. Keep the MCP for the first CLI+skill release, but make it a thin adapter over the same core and use the same canonical identity; consider MCP removal only after real CLI+skill use is validated.
3. Rename the complete portable skill/project root to `browser-automation/`, keep `SKILL.md` at that root, bundle `scripts/browser`, and keep `uv run --frozen` plus environment preparation behind the launcher.
4. Make `SKILL.md` name the launcher only as the relative resource `scripts/browser`. The agent resolves that relative path from the directory containing the exact `SKILL.md` locator advertised by the runtime; do not assume a framework-populated shell variable, use `$CODEX_HOME` or another vendor-specific home, install a PATH command, or embed a checkout-specific absolute path in the skill.
5. Remove `close_browser` from the initial CLI/skill-facing surface, restrict screenshot output paths, define URL schemes, and use stable error codes rather than Python exception names.
6. Keep first-class click/type/fill outside this conversion unless the user explicitly expands product scope; teach selector-based interaction through existing `dom_snapshot` + `run_script` capabilities.
7. Preserve the implemented clean generic boundary: `browser-automation` skill/folder/server identity, `scripts/browser`, CLI identity `browser`, `scripts/browser-mcp`, and `browser_automation` package namespace. Retain the AutoByteus term only in genuine ownership metadata or immutable history/evidence, never in the capability contract or a compatibility alias.
8. Make the skill's normal CLI usage argument-isomorphic with retained MCP operations: approved task commands and operation-specific flags, direct scalar values, direct JavaScript via `--script`, and structured `run_script.arg` via `--arg-json`. Keep file/stdin modes as optional input-source escape hatches, not a complexity-based agent preference.
9. Remove the `brui-core` runtime dependency and reimplement only the used browser config/availability/launch/connect subset inside `browser_automation.runtime`. Do not vendor the entire library, retain a `brui_core` compatibility namespace, import from the parent checkout, copy unused UI/clipboard/singleton/global-kill code, or modify/deprecate the external library for its other consumers.
10. Make Chrome establishment atomic across supported processes. Every caller must acquire the per-port establishment gate before its authoritative endpoint probe. Keep that gate held by a newly launched owner after `/json/version` readiness until initial Playwright connection and first-context validation either promote the process irreversibly to external durable state or abort and finish exact owned-group cleanup. A ready endpoint observed only after acquiring an otherwise-unheld gate is attach-first/durable and gives the caller no kill authority.

## Out of Scope

- A generic framework that converts every MCP in the repository into a CLI.
- First-class click/type/fill/select commands not present in the current public browser MCP.
- Firefox/WebKit support; the approved owned runtime and target-identity mechanism are Chromium/CDP-specific.
- Cloud-hosted browser orchestration or multi-user remote service authentication.
- Automatic handling of captchas, MFA, purchases, messages, account changes, or other external side effects without normal agent confirmation policy.
- Modifying the image/audio CLI or retroactively creating its missing skill.
- Persisting or migrating the current process-local short numeric tab IDs.
- Modifying, deleting, or republishing the separate `brui_core` repository/package; it remains available for other consumers.
- Creating a new generic shared browser-runtime library or copying unused `brui_core` UI/clipboard APIs into this bundle.

## Constraints / Dependencies

- The current candidate delegates first-context connection and auto-launch to `brui-core==2.0.0`; SR-008 removes that dependency while preserving the approved observable behavior through owned Playwright/Chrome code.

- The wrapper is expected to depend on `uv` and use the project lockfile.
- The agent runtime must advertise the exact `SKILL.md` locator through its system-prompt catalog or provider-specific skill projection. This locator is model-visible resource context, not a populated shell variable or an agent-facing `load_skill` operation.

- Large page/script **results** use the approved optional workspace-safe artifact-output contract; overwrite is opt-in. Input complexity does not by itself require a file/stdin source.
- The original streamable-HTTP MCP default bound to `0.0.0.0` without authentication; the checkpointed candidate already validated loopback default plus an explicit non-loopback warning. SR-006 preserves that behavior and adds no remote-auth system.

## Resolved Material Decisions / Remaining Questions

1. Retain MCP for the first release only as a thin adapter over the same browser application boundary used by the CLI; remove process-local identity and duplicated tool business logic.
2. Use browser-owned CDP target IDs across independent CLI/MCP calls; do not add a daemon or preserve short numeric aliases.
3. First release supports Bash-capable macOS/Linux coding-agent environments and the existing Chrome/Chromium-over-CDP runtime; other shells/platforms are follow-up validation targets.
4. `list-tabs` lists every addressable page in the first configured Chrome context; the context endpoint/configuration is the isolation boundary for this release.
5. `read-page`, `dom-snapshot`, and `run-script` support optional workspace-safe output files; existing files are rejected unless explicit overwrite is requested.
6. `run-script` is retained but appears only in a clearly marked advanced skill workflow and remains subject to normal confirmation for consequential external side effects.
7. The retained streamable-HTTP MCP default becomes loopback-only (`127.0.0.1`); explicit non-loopback configuration is operator opt-in and warns that no built-in authentication exists.
8. The tracked MCP stdio launcher is retained by capability but cleanly renamed to `scripts/browser-mcp`; both prior wrapper names are removed rather than forwarded.
9. The generic public naming set is fixed as: skill/folder/server `browser-automation`; heading/display **Browser Automation**; agent launcher `scripts/browser`; CLI help identity/console entry `browser`; MCP wrapper `scripts/browser-mcp`; package namespace `browser_automation`; distribution `browser-automation`; generic capability-prefixed environment/readiness/schema identifiers. Product provenance is confined to author/origin ownership metadata and history.
10. The normal agent command maps former MCP inputs directly to flags. In particular, `run_script(tab_id, script, arg)` becomes `run-script --tab-id ... --script '<JavaScript>' --arg-json '<JSON>'`. File/stdin sources remain supported only as optional alternate sources, not the skill's recommendation for complex code.
11. Browser automation owns its narrow runtime implementation and depends directly on Playwright/standard-library mechanisms; the external `brui_core` package/repository remains separate for other consumers. Absorb/reimplement only behavior required by `BrowserRuntime`, not the whole library or its namespace.
12. Cross-process launch establishment is atomic through promotion/abort: every caller gates before authoritative readiness classification; a launch owner holds the gate across readiness and initial connect/context validation; `promote()` removes abort authority before unlock, while `abort()` completes exact owned cleanup before unlock. The lock carries no durable browser state.

No material requirement question remains open for initial design. Platform/CDP protocol compatibility and concurrent-client behavior remain implementation-validation risks, not unresolved product intent.
